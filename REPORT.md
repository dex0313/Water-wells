# Water-wells — финальный отчёт агента

Ревизия проекта `Water-wells-main` (ESP32 + EBYTE E22, PlatformIO, Arduino, MQTT → Home Assistant) по документу «инструкции агенту по исправлению кода и подготовке к репитеру».

**Проверено:** `cppcheck`-эквивалент не запускался (недоступен в среде), но все сборки идут с `-Wall -Wextra` **без единого предупреждения**; проводной формат v1 защищён `static_assert` и golden-тестом T-1. Хост-компиляция подтверждена: `MeshPacket = 59`, `DataPayload = 32`, `AckPayload = 5` (v1.1 с `seq`).

### Фаза 2 (репитер)
- **R1** — `counter = (uint16_t)esp_random()` при `loraInit()`; обоснование (совместимость со старыми нодами через TTL 45 с) задокументировано в коде и README.
- **R2** — дедуп по (source, packet_id) на всех ролях (централизованно в `lora_rx.cpp` после валидации кадра); BASE принимает DATA/ACK/STATUS только при `destination == BASE_ID || 0xFFFF`; NODE принимает CMD только при `source == BASE_ID`; повторная команда с новым `packet_id` не является дубликатом (идемпотентна).
- **R3** — очередь TX: 8 элементов, приоритеты `TXP_ACK < TXP_CMD < TXP_FWD < TXP_DATA`, при переполнении вытесняется элемент с наименьшим приоритетом (иначе дропается новый), `assign_new_id` для своих пакетов (CRC пересчитывается), `assign_new_id=false` — пересылка байт-в-байт; `txPoll()` — конечный автомат IDLE→writing→wait_done (AUX LOW→HIGH, игнор первых мс, защитный таймаут `2*LORA_AIRTIME_MS+500`); пауза после RX (`LORA_TX_AFTER_RX_GAP_MS`, TODO(owner)); `waitAux` с блокировкой остался только в init/setMode; приём не блокируется; `sendData/sendCommand/sendAck` — обёртки над `txEnqueue`.
- **R4** — `include/dedup.h`, `src/dedup.cpp`: кольцо 64, линейный поиск, TTL 45 000 мс, время передаётся параметром (хост-тесты), метка не обновляется при повторном попадании, счётчик `dedupEvictedLive()` (должен оставаться 0).
- **R5** — `[env:repeater]` (`-D ROLE_REPEATER -D NODE_ID=200`), без реле/ZMPT/MQTT, BME опционально, всегда WDT+LoRa+NVS-счётчик; диапазон 200..250 зафиксирован `static_assert`; `ROLE_NODE + FEATURE_REPEATER` — для подстанций; собственные эхо/адресованные себе пакеты не пересылаются.
- **R7** — пересылка после случайного джиттера 100…600 мс; приоритет по типу (ACK/CMD/FWD); лимит `FWD_MAX_PER_MIN=30` (дроп с логом и `fwd_drop`); в кэш дедупа попадают и CMD/ACK; мусор не ретранслируется (парсер фильтрует до диспетчера); локальные CMD к репитеру отвечают NAK.
- **R8** — (1) heartbeat репитера раз в `SENSOR_INTERVAL` с джиттером: `PKT_DATA` с `num_relays=0, num_sensors=0` и BME (или NaN) — старый BASE покажет «онлайн» и температуру; (2) `PKT_STATUS=4` (uptime, boot_count, fwd, rx_dup, fwd_drop, rx_crc_err, resync_bytes) раз в 10 мин — старый BASE молча игнорирует, новый публикует `lora/node_<id>/stats/*` с discovery-сущностями категории diagnostic.
- **R9** — BASE: считает дубликаты, принимает пакеты через репитер без отличий, ждёт ACK по формуле для 2 хопов, отслеживает репитер как обычную ноду.

### 2.1 Правки по итогам ревью (пост-ревью)

- **PR-1 (Serial до `relaysInit`)** — `setup()` теперь начинается с `Serial.begin(115200)` + `delay(10)`, затем `relaysInit()` (только NODE). Диагностика «[NVS] Relay states loaded/restored» больше не теряется: до `begin()` ядро ESP32 Arduino молча отбрасывает вывод. Гарантия P0-6 не тронута: `Serial.begin()` конфигурирует только UART-пады (GPIO1/3), первой операцией с пинами реле остаётся `gpio_set_level` (latch) → `pinMode` внутри `relaysInit()`; цена — ~10 мс сдвига старта реле.
- **PR-2 (дедуп в очереди публикаций, P1-1.7)** — `pubEnqueue()` (BASE) пропускает точный дубликат (topic+payload), уже лежащий в очереди. Ранее, если `publishDiscovery()` лишь частично помещалась в очередь (`PUB_QUEUE_SIZE=40`), флаг `discovered[]` не ставился и повтор запускал burst с нуля, задваивая уже поставленные в очередь сообщения; при затяжной перегрузке очереди дубликаты размножались (retained-конфиги идемпотентны — не опасно, но очередь захламлялась и прогресс не накапливался). Теперь повтор добавляет только недостающие сообщения и burst завершается по частям; тот же топик с ДРУГИМ payload (пустой `HA_DISCOVERY_CLEANUP`-пейлоад после сокращения профиля) ставится как обычно — доставляются оба, побеждает последний. Эффект распространяется и на `sendBaseDiscovery()`/`publishStatusDiscovery()` (те же флаги «только на полный успех»). Сканирование — по кэшированным длинам строк, максимум 40 сравнений на enqueue, влияние на CPU пренебрежимо.
- После правок: сборки `base`/`node`/`repeater` — SUCCESS без предупреждений (`-Wall -Wextra`), native-тесты 39/39.

### 2.2 Выбор LoRa-модуля и relay-only сборка (FR-1 / FR-2)

- **FR-1 (модуль E22/E220)** — новый `include/lora_module.h`: ровно один модуль на сборку — `LORA_MODULE_E22` (по умолчанию, текущее железо) или `LORA_MODULE_E220` (скважины за репитером), выбор через `platformio.ini` (пример — `[env:node_e220]`). Оба модуля имеют одинаковый пинат (M0/M1/AUX/UART), переключение режимов и прозрачный формат, поэтому рантайм-PHY (`lora_phy.cpp`) общий; различаются карты регистров (у E220 NETID по адресу 0x02 сдвигает REG0..REG3 и CRYPT на байт выше, кадр 9 байт против 8) — они нужны только опциональному программированию модуля из firmware. `LORA_UART_BAUD` (9600) — именованная константа прозрачного UART; в лог старта добавлено имя модуля («LoRa init done (E22-400T33D)»).
- **FR-1 (автоконфиг, опционально)** — `LORA_MODULE_AUTOCONFIG=1` (по умолчанию 0 — текущее поведение не меняется: модуль конфигурируется инструментом EBYTE один раз): в sleep-режиме (mode 3, UART фиксированно 9600 8N1 у обоих модулей) firmware пишет постоянный профиль (0xC0) и верифицирует его чтением (0xC1) с таймаутами и ожиданием AUX; несовпадение НЕ фатально (P0-1) — модуль остаётся на профиле от конфигуратора, в логе предупреждение. Байты профиля `LORA_CFG_*_VALUE` — заглушки: до включения владелец должен сверить их с datasheet выбранного модуля и добавить `-D LORA_CFG_PROFILE_VERIFIED` (до этого сборка даёт `#warning`). Проверено: компилируется для обоих модулей, `#warning` выводится как задумано.
- **FR-2 (FEATURE_SENSORS=0)** — новый флаг в `config.h` (по умолчанию 1): полностью исключает из компиляции локальные сенсоры — BME280 (Wire/I2C, детекция, ретраи) и ZMPT101B (ADC, калибровки, пороги, массивы пинов в `config.h` тоже под флагом). Реле (P0-6) не затронуты: NVS-восстановление, команды, ACK, отложенный отчёт. Профиль ноды форсируется в `NODE_NUM_SENSORS=0`; отчёты несут t/h/p = NaN и num_sensors = 0 — BASE не создаёт сущности температуры/влажности/давления/напряжения/мотора, а `HA_DISCOVERY_CLEANUP` подчистит устаревшие. Флаг независим от роли: на BASE убирает локальную публикацию BME, на REPEATER — опциональный опрос BME. Выигрыш flash для ноды: ~35 КБ (318 477 → 283 201). Сборки: `[env:node_relay_only]`, комбинация `-D LORA_MODULE_E220 -D FEATURE_SENSORS=0` проверена отдельно.
- Попутно: `sensor_manager.cpp` теперь явно включает `<Arduino.h>` (раньше он приходил транзитивно через Wire/Adafruit — в relay-only сборке это сломало бы компиляцию); статик-ассерты `NODE_NUM_SENSORS >= 1` действуют только при включённых сенсорах.
- После правок: `base`/`node`/`repeater`/`node_e220`/`node_relay_only` — SUCCESS без предупреждений (`-Wall -Wextra`, предупреждение `-Wtype-limits` на цикле печати при NODE_NUM_SENSORS=0 устранено), native-тесты 39/39.

## 5. Принятые технические решения (отклонения/уточнения)

1. **`espClient.setTimeout(3000)` не установлен** (P1-2.3). Семантика `WiFiClient::setTimeout` меняется между ядрами (секунды в 2.x vs миллисекунды в части API 3.x) — неверная единица дала бы 3-мс сокет-таймаут на 3.x и сломала бы MQTT. Использован `client.setSocketTimeout(3)` (секунды, документировано для PubSubClient) — эффект тот же: блокировка `mqttConnect()/loop()` ограничена секундами.
2. **Коммиты сгруппированы**, а не «одна задача = один коммит»: задачи переплетены в одних и тех же файлах (например, `sensor_manager.cpp` содержит P0-1, P0-6, P1-5, P1-6, P1-7). История: baseline → переработка (перечень ID в сообщении) → тесты → P1-9 (3.x) → docs. По-задачная детализация — в этом отчёте.
3. **`loraLoop` извлекает кадры после каждого байта** (push→pop), чтобы скользящий буфер (2 кадра) не переполнялся на пачках ACK+DATA; поведение парсера покрыто тестом «пачка кадров байт-в-байт».
4. **`bad_relay` по P0-4 применён буквально** (`ever_seen && relay_idx >= num_relays`): нода, видимая только по ACK (профиль неизвестен, num_relays=0), отвергнет команды с `failed:bad_relay`. На практике ноды присылают DATA раньше команды, профиль известен; репитеры (0/0) корректно защищены от команд.
5. **Порядок выкатки** (BASE → репитер → ноды) продублирован в README; BASE совместим со старыми нодами: `seq`-эхо опционально, ACK 5 байт принимается проверкой `payload_size >= 4`, DATA старых нод валиден, неизвестные типы игнорируются.
